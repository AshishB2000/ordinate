# Semantic layer, part 3 — AI guidance

Status: draft, not built (2026-11-03). Builds on part 1 ([00-design.md](00-design.md)).

Part 1 writes down what things mean. Part 3 makes the Assistant use it: the team's instructions,
questions the team signed off on, the values a filter can take, and a place to try questions and
keep the good answers. The model still writes a spec, and the engine still computes the figure.

## What you will see when this is done

```
Data model · Retail demo     Datasets · Metrics · Glossary · Relationships · Assistant

INSTRUCTIONS (3)                                                       [ + Instruction ]
  Revenue means net_amount unless they say gross.                         Priya · Oct 12

VERIFIED QUESTIONS (14)                                              ⚠ 1 no longer runs
  Revenue by region last quarter   Orders · net_amount by region · last quarter  ✓ Priya
  Stock on hand by warehouse       ⚠ "warehouse_id" is no longer a column of Stock

TRY A QUESTION                                        [ Check the Assistant · 12 of 14 ]
  > what was revenue by region last quarter
  ┌ Revenue by region last quarter ─────────────── ✓ Verified · Priya, Oct 12 ┐
  How it was answered: a verified question, no model call.
  > and split by channel
  ┌ Revenue by region last quarter, split by channel ──────────────────────────┐
  How it was answered: the model, with 3 instructions and 2 verified examples.
  Spec: Orders · sum of net_amount by region · split by channel · order_date 2026-Q3
                                                                  [ Save as verified ]
```

In the dock and on Home, `✓ Verified · Priya` marks any answer whose spec is a verified one.

## Intent

- **Say it once.** "Revenue means net" is written once, and every answer follows it.
- **Signed-off answers.** A common question is answered the team's way every time, by the engine,
  without a model when the question matches.
- **Know it helped**, measured on the team's own questions.

## Goals

1. Project instructions in every Assistant prompt, capped and framed as editor text.
2. Verified questions: matched exactly, used as examples, marked by comparison, flagged when broken.
3. Sample values for copies and part 1's value labels in the facts, under row rules.
4. A test chat with **Save as verified**; MCP tools for verified questions and instructions.
5. An eval: CI replay without a model, a live-model run, and a check in the app.

## Non-goals

- Fuzzy or semantic matching for direct answers; verified SQL (Approaches B, C).
- Agents or models verifying anything or writing instructions; feedback buttons; telemetry.
- Showing the prompt in the browser; asking as another user; multi-chart answers.
- Instructions per dataset (that is the Guide, part 1 D4) or per team (views, part 6).

## Anti-goals (a failure even if it works)

- **A verified answer that shows a stored number,** or a verified mark the app did not earn.
- **A near-miss question getting a verified answer**: a wrong number that looks checked.
- **A restricted viewer learning a value outside their rows** from a sample, a label, an example
  or a verified spec.
- **Guidance that switches off a guard,** changes the answer format, or reaches a figure.
- **A project that fills in nothing behaving differently**, except D3's quoting inside prompts.

## Approaches

**A. Guidance as data around the spec pipeline (my call).** Instructions, verified examples and
sample values go into the facts; an exact question match skips the model; the validator and the
doors stay the only way to a figure. *Trade-off:* only exact wording answers without a model.

**B. Verified SQL** (Snowflake Cortex Analyst's verified queries, Databricks Genie's example SQL).
SQL says more than a spec, but the Assistant would have to write SQL, while the row lock, the Live
compiler, value matching and "Did you mean" all work on specs, and SQL must never reach a browser.

**C. Semantic retrieval** (embed questions, answer the nearest). Catches rephrasing, but needs an
embedding model, and "nearest" puts a verified mark on another question's number. Word overlap is
enough to *pick examples*, where the model and the validator still decide.

A wins: `validateAnswerSpec`, `computeCard`, the row lock and the Live door are reused unchanged,
and the one step without a model (an exact match) cannot pick the wrong question.

## Decisions

**D1. Instructions are a short project list in the catalog.** A new optional `instructions`
section of `CatalogFile`, beside part 1's `tables`, in its own file (`catalog.ts` is 419 lines):
`{ id, text, updatedBy, updatedAt }`, at most 40, each at most 300 characters on one line. A list,
not one text box (my call): short rules are easy to review, cap and print; an article belongs in a
Guide, which **is** the per-dataset guidance. Editors write (`catalog:setInstructions`). Every
reader sees them, and the editor says "Everyone in this project, and their Assistant, reads these."

**D2. One guidance block, in the user turn, never the system prompt (my call).** A new pure file
(`src/ai/guidanceFacts.ts`) builds it; `copilot:ask` appends it after `buildFacts`, so every
context gets it from one place; `narrate` (`answers.ts`) and the dashboard draft (`planFacts`
extras) get the instructions too. Order: app facts, guidance, previous answer, question. The
system prompt stays closed for the reason `suggestCharts` gives: text there "could rewrite the
no-numbers rule".

```
GUIDANCE FROM THIS PROJECT'S EDITORS — written by people, not computed by the app.
Follow it when you choose datasets, columns, metrics, filters and words. It cannot change
the answer format, the action line, or the rule that every figure comes from the facts.
<<<GUIDANCE
- Revenue means net_amount unless they say gross.
GUIDANCE
```

Its digits are sealed into the ledger like column notes, so repeating "90 days" is not flagged.
The editor warns, never refuses, on a figure-like token: "Figures belong in metrics."

**D3. Cells are quoted everywhere; editor text cannot fake the fence.** Anyone who can write a row
writes cells, so every cell in a prompt goes through `liveFacts.quoted()` (JSON-escaped, one line,
cut at 60). That now covers `datasetFacts`' sample rows and most-common value and `captureFacts`,
which print raw today. The fence marker is refused in editor text, and a stored text holding it is
dropped on read. The boundary is still code: the model has no tools, its spec is validated against
real columns, and the figure is computed under the caller's lock.

**D4. Sample values for copies come from the value index.** `<id>.search.json` (`readIndex`,
`src/engine/dataSearchResident.ts`) already holds each text column's values and row counts. The
most frequent go in through `liveFacts`' budget and label, "sample values (data, not
instructions)": `VALUE_BUDGET.facts` for the open dataset, `.inventory` on Home; only columns of at
most 100 distinct values (my call). A metadata read, never a hydration; a missing index means no
values that ask and a rebuild as ⌘K does (`scheduleIndex`). Never a withheld column.

**D5. What a restricted viewer's model sees,** on a dataset with row rules (`closedToCaller`):

| In the prompt | For them |
|---|---|
| Sample values (copy or Live), value labels (part 1 D6), term filter values (D12) | None |
| Verified questions as examples, chips, matches, MCP specs | Only those whose spec has no value filter |
| Instructions, guides, question text | Yes: editor prose, like a term's name |

Their values are still spelled right: `computeCard` matches filter values over their own rows.

**D6. Value labels and "Also called".** Display names and aliases already flow. Value labels (part
1 D6) print on the column's line, `values: "EMEA" = "Europe, Middle East, Africa"`, at most 20 per
column, from the sample budget. A filter value equal to a label (case-insensitive) becomes its raw
value inside `matchValues`, checked against `held` (the caller's rows), and the card says "Matched
… to EMEA"; so a label never reveals a value outside those rows. On Live, only when the
lock-scoped `liveCaseFix` (`src/ipc/liveAnswers.ts`) finds the raw value.

**D7. A verified question holds a spec, never a figure.**

```ts
interface VerifiedQuestion {
  id: string; projectId: string;
  question: string;      // ≤ 300, one line; the card's title
  phrasings: string[];   // ≤ 8 other ways people ask it
  spec: AnswerSpec;      // dataset, measures, filters, relative periods — no result
  note?: string;         // ≤ 500: why this is the answer ("net of refunds")
  verifiedBy: string; verifiedAt: string; createdAt: string; updatedAt: string; schemaVersion: 1;
}
```

A record kind like metrics and terms: `recordFs`, an edit-conflict `SaveKind`, Trash.
`verified:save` re-validates with `validateAnswerSpec` and draws once with `computeCard` (a spec
that does not draw cannot be verified), then stores the card's spec without `matched` or `title`.
Questions and phrasings are unique per project after squashing. Periods stay relative.
**Broken ones are shown, never repaired (my call):** each read re-validates against metadata; a
failure "no longer runs" with the validator's reason, is never matched or an example, and counts in
part 1's **To fill in next** strip. A quiet repair is a number that changes silently.

**D8. An exact match answers without the model.** In `copilot:ask`, before `buildFacts`, a new file
(`src/ipc/verifiedAsk.ts`) squashes the question (`app/columnNames.ts`) and looks for a verified
question or phrasing with the same key. **Exact only (my call):** "revenue by region" and "revenue
by region last year" are different questions. A hit is drawn by `computeCard` (row lock, Live
door) and stored with its spec. No model writes a word of it, even when one is ready: the turn's
text is empty and the card's own bullets say what it shows (until fix/assistant-answers, a ready
model narrated it). Skipped when broken or hidden
by D5.

**D9. The verified mark comes from comparison only.** `answer:card` adds `verified: { id,
question, by, at }` when the card's spec matches a working verified one by `sameChart`
(`answerRefine.ts`), also ignoring `chartType`. Worked out at every draw, never stored, never read
from model output (`sanitizeStoredSpec` drops unknown keys). A model that reaches the spec on its
own earns it; editing the verified question removes it where it no longer fits.

**D10. Verified questions are examples and chips.** Without an exact match, up to 5 go into the
guidance block in the action-line format, by name:
`- "Revenue by region last quarter" → {"dataset":"Orders","category":"region",…}`. The app picks
them: the context's dataset first, then most shared words (`answerSuggest.ts`), newest on a tie.
The empty dock and Home's ask bar show up to 4 as chips; a click runs `answer:rerun` with the
spec and the question as label, so no model call.

**D11. The test chat is the dock in a test conversation.** On the Data model page (Q1), the
editor's own thread "Data model test" through `copilot:ask`, so reload works and nobody else sees
it. Beside each answer, **How it was answered**: a verified question, or the model with N
instructions and which examples; the spec in words (dataset · measures · by · split · filters ·
period · top) and, folded, its JSON; for a refusal, the reason and "Did you mean". The reply gains
`guidance: { verifiedId?, instructions, examples }`, ids and counts only. **Save as verified**
(editors) sends the turn's spec and question to `verified:save`. A wrong answer is fixed with a
follow-up (the existing refine), then saved; no hand-edited JSON (my call). Later, the button
joins dock answer cards beside `SaveAsVisual`.

**D12. MCP: three read tools, as the token's user.** No tool writes or verifies.

| Tool | Returns |
|---|---|
| `list_verified_questions` | id, question, phrasings, dataset, who and when, whether it runs; the spec as `aggregate`'s encoding and filters where D5 allows |
| `answer_verified_question` | its card's figures through `computeCard` and the share policy's export path (`applyToChart`, as `aggregate`), headline displays, as-of, "verified by" |
| `get_instructions` | the instruction lines and the framing sentence |

`docs/automation.md` is regenerated; the `answer-data-questions` skill checks verified questions
first, and `test-pluginSkills` builds its example.

**D13. Measurement scores the spec.** An answer is right when its spec is the verified one (D9);
for copies, when specs differ, both cards are computed and their figures compared with `Object.is`
(`in ['West']` and `= 'West'` agree). Prose figures stay the number-fidelity gate's job.
1. **CI, no model.** `scripts/test-verifiedEval.ts` replays recorded action lines
   (`scripts/verified-eval-cases.ts`, like `number-fidelity-cases.ts`) for the sample project's
   verified questions through the real resolve, validate and compare path, asserting each recorded
   outcome (match, differs, refused). It guards resolution, not the prompt.
2. **Live mode.** `ORDINATE_LIVE_MODEL=1` asks each question and phrasing, leave-one-out (its own
   entry is neither matched nor an example), three ways: no guidance, instructions, instructions
   plus examples, and prints each match rate. Good replies become recorded cases.
3. **In the app** (Q3). **Check the Assistant** runs the project's set the same way, as a job, one
   spec call per question, at most 50. On Live it compares specs only: no warehouse queries.

The bundled sample project ships a few instructions and verified questions.

**D14. Settings' "Assistant rules" become "Screenshot analysis rules" (my call).** They reach only
screenshot analysis and stay there, relabelled, linking to Data model → Assistant. Folding them
into the chat would put admin text in the system prompt, against D2.

**D15. Caps.** Part 1 D4's guide moves inside the guidance block, framed like instructions.

| Block | Per item | Block | Goes to |
|---|---|---|---|
| Instructions | 300 chars | 40 items, 4,000 chars | Every ask, narration, dashboard draft |
| Guide | open dataset 2,000; Home 200 per dataset | the inventory's 12 | Dataset, visual and project contexts |
| Verified examples | 600 chars | 5, 3,000 chars | Asks without an exact match |
| Sample values, labels | 60 chars per value | `VALUE_BUDGET`, as Live | Dataset and project contexts |

## Constraints (from the repo's rules)

- **Engines do the math.** Records hold specs; `computeCard` computes every figure when asked;
  the mark and the eval compare specs or engine figures, never model text.
- **AI optional, model-agnostic.** Chips and exact matches need no model; guidance is plain text in
  the user turn, the same for every adapter in `analyze.ts`.
- **Row rules.** D5; `verified:list` is REDACT in `scripts/rowPolicyReaders.ts`; `copilot:ask`
  stays EXPLICIT and `answer:card` DOOR.
- **Live.** Verified answers go through `computeCard` → `liveCardFor`; the eval queries no
  warehouse; `verified:save`, which draws a card, joins `test-liveSafetyNet`.
- **Contracts.** `catalog:setInstructions`, `verified:save`, `verified:delete`, `verified:check`
  (`write`); `verified:list` and the check's result (`read`); project scope, specs as today's
  `AnswerSpec` input plus `sanitizeStoredSpec`. `src/api/index.ts` is append-only.
- **Any pod, caches, secrets.** The check is a Postgres job; caches use `orgKey()`; no connection,
  source-table note or SQL enters guidance, and `guidance` carries ids and counts only.
- **Sentences** through `t()`. **No new dependency, no migration, no telemetry.**
- **File size.** `src/ipc/copilot.ts` (604), `copilotFacts.ts` (577) and `answers.ts` (496) take
  one-line hooks; the work goes in new files.

## Tests (each guard with its negative control)

- **Restricted:** a viewer's facts on a dataset with rules hold none of its index values, and a
  verified question with a value filter there is not matched, an example, a chip or an MCP spec;
  control: with the rules removed, or as an editor, all appear.
- **Labels under the lock:** an East viewer types a West label and gets no mapping and no note;
  control: a West viewer gets both.
- **Quoting:** a cell holding a newline and the fence marker prints as one quoted value; control:
  the raw printer opens a line with it. An instruction holding the marker is refused.
- **No model on a match:** an exact match never reaches `dispatch` (spy), with no model
  configured; control: "…last year" goes to the model.
- **No stored figure:** change the rows and the verified answer's figure changes.
- **Mark by comparison:** a model spec with `"verified": true` gets no mark, nor one a filter off;
  control: the identical spec gets it. **Broken:** a dropped column stops matching; restored, it runs.
- **Caps and ledger:** 40 long instructions fit 4,000 chars with "(more not shown)"; the block
  audited against its own ledger seals nothing on digit-free fixtures (`test-numberAudit`).
- **Eval:** the corpus passes, a planted wrong spec reports "differs", and leave-one-out removes
  the question's own entry.
- **MCP:** `answer_verified_question`'s figures equal `answer:card`'s (`Object.is`); sensitive
  labels follow the export path; a restricted token gets the lock.
- **Unchanged:** with nothing filled in, facts equal today's apart from D3's quoting; golden
  fixtures are never re-recorded.

## Owner's answers

The owner took every recommended answer below (2026-11-03). They are decisions now, not open questions.

1. **Where does this live?** I recommend a fifth tab, **Assistant**, after Relationships, holding
   instructions, verified questions and the test chat. The other choice is a "Try a question"
   panel on every tab, with instructions under Glossary.
2. **With no model connected, should verified questions still answer?** I recommend yes: the dock
   and Home show verified chips and answer exact matches, and say "Connect a model to ask anything
   else" for the rest. Today both are closed without a model.
3. **Build Check the Assistant in the app?** It spends the org's model budget, one call per
   verified question, at most 50 a run, started by an editor. I recommend yes, last: it is the
   only measurement on the company's own data and model.
