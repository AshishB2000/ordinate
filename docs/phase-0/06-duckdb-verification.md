# DuckDB verification — measured results

**DuckDB 1.5.5** (Homebrew, arm64) · macOS 25.5.0 · Node v24.14.0 · run against the §7 script in [README.md](README.md).

Every `NEEDS VERIFICATION` marker in the Phase 0 documents is resolved below by **execution, not inference**. Fixtures and commands are reproducible; the fixture set is regenerated by the shell block at the end.

**Six predictions were wrong.** They are corrected here and in the affected documents. Four favour the migration, two make it harder.

---

## 1. Corrections to Phase 0

### ✅ REFUTED — `sum` of a text column does **not** silently cast

This was **Tier 1, finding #1** — the top-ranked silent-wrongness risk in the whole analysis.

```
D8: SELECT sum(x) FROM (SELECT '5' AS x);
→ Binder Error: No function matches the given name and argument types 'sum(VARCHAR)'
D9: SELECT sum(x) FROM (VALUES ('007'),('012')) t(x);
→ Binder Error (same)
```

DuckDB has **no implicit VARCHAR→numeric coercion for aggregates.** `sum('007')` does not return 7; it refuses to bind. That moves the finding from **Tier 1 (silent wrongness) to Tier 2 (loud failure)** — still a breakage requiring the declared-type gate in TypeScript, but it cannot ship a wrong number to a dashboard. It fails at query time, visibly.

The related `metricValue` finding (`min` of a text column returning the string `'007'`) still stands, because `min(VARCHAR)` **is** a valid binding.

### ✅ REFUTED — DuckDB does not use Kahan summation; float sums match JS exactly

```
D1: SELECT sum(x) FROM (VALUES (0.1),(0.2),(0.3))    → 0.6000000000000001
    JS  [0.1,0.2,0.3].reduce((a,b)=>a+b,0)           → 0.6000000000000001   ✅ identical
D2: SELECT sum(x) FROM (VALUES (1e16),(1.0),(-1e16)) → 0.0
    JS  [1e16,1,-1e16].reduce((a,b)=>a+b,0)          → 0                    ✅ identical
D3: sum(x)/count(x) = avg(x)                          → true (exactly)
```

The D2 probe is decisive: Kahan compensation would give `1.0`, a naive left-to-right fold gives `0.0`. DuckDB gives `0.0`. **`transforms` T14, `datasetStats` R-STATS-04, and `metricValue` R-METRIC-02 are not at risk from summation order** on these probes, and `avg` need not be decomposed into `sum/count` for fidelity.

Caveat worth keeping: this tested a 3-row single-threaded aggregate. It does not prove bit-identity for a parallel reduction over a million rows with a different partition split. The float→text retype hazard (a `0.30000000000000004`-shaped result flipping a column to text) is now **unlikely**, not impossible.

### ✅ REFUTED — quoted `""` and unquoted empty are both NULL

```
A7: fixture `a,b\n"",`  → a IS NULL = true, b IS NULL = true
```

Predicted a distinction that would leak empty strings into `ParseResult`. There is none — **this matches current behaviour exactly** and needs no post-processing. Remove it from the "not covered by the mitigation" list.

### ✅ REFUTED — header whitespace is trimmed, and JSON key order is first-seen

```
A6: header `  a  ,b`                        → columns a, b            ✅ matches
C1: read_json_auto('[{"a":1},{"b":2,"a":3}]') → columns a, b (in that order)  ✅ matches
```

Both were flagged as likely breakages. Neither is. JSON key order in particular was a risk to every saved visual's encoding — it is fine.

### ✅ REFUTED (and a real win) — `date_diff` already counts boundary crossings

```
F7: SELECT date_diff('year', DATE '2023-12-31', DATE '2024-01-01') → 1
```

One day apart, one year boundary crossed → `1`. This is **Tableau semantics, which is what `formula.ts` implements.** The brief listed "DuckDB's `date_diff` measures differently" as a translation hazard (landmine 6.2). It does not. `DATEDIFF` translation is materially cheaper than the formula spec assumed.

### ❌ WORSE THAN PREDICTED — ragged rows lose the header, or gain a phantom column

The spec predicted "DuckDB errors, or `ignore_errors` drops the row." Both are wrong, and the reality is worse:

```
B1: FROM read_csv('ragged.csv')                              -- a,b,c / 1,2 / 3,4,5,6
    → columns: column0,column1,column2,column3
    → rows:    3,4,5,6
```

**The default read silently discarded the header row *and* the short data row**, keeping only the widest line and synthesising positional names. No error, no warning. A three-row file returns one row.

```
B2: ... null_padding=true, ignore_errors=true
    → columns: a,b,c,column3
    → rows:    1,2,NULL,NULL  /  3,4,5,6
```

With padding, the header survives — but the overflow field creates a **phantom fourth column** rather than being truncated. Current behaviour truncates the `6` and warns. `columns={...}` with an explicit 3-column schema is a hard sniffer error (B3).

**Assessment:** `parse` R-PARSE-03 is the single hardest ingest breakage, and no `read_csv` option combination reproduces truncate-and-warn. The row-shape repair must stay in TypeScript, or the file must be read with a schema wide enough to hold the widest line and then narrowed.

### ❌ WORSE THAN PREDICTED — `trim()` strips NBSP but **not** tab

```
E1: trim(TAB || ' x ' || TAB)   → "\t x \t"   (tab NOT stripped)
E2: trim(NBSP || 'x' || NBSP)   → "x"         (NBSP stripped)
E7: regexp_full_match(TAB,  '\s*') → true
    regexp_full_match(NBSP, '\s*') → false    (RE2 \s excludes NBSP)
```

The spec assumed "spaces only." The truth is stranger: `trim` and RE2's `\s` cover **complementary halves** of the JS whitespace class. Neither alone is correct, and combining them naively still misses cases. The explicit character-class macro is mandatory, and it is now verified to work:

```
G8: CREATE MACRO sc_empty(x) AS (x IS NULL OR regexp_full_match(CAST(x AS VARCHAR), '[ <TAB><NBSP>]*'));
    sc_empty('  ') → true    sc_empty('x') → false
    sc_empty(NULL) → true    sc_empty(5)   → false     ✅ accepts ANY-typed args
```

## 2. Landmine 6.1 (`007`) — real, but conditional, and the condition is the dangerous part

This deserves its own section because the answer is neither "the brief was right" nor "the brief was wrong."

```
A1: SELECT typeof(code), code FROM read_csv('leadzero.csv')   -- 2-row file, 007/012
    → VARCHAR, '007'        ✅ NOT corrupted
```

DuckDB 1.5.5's sniffer **rejects leading-zero integer candidates.** On a small file, `007` survives as VARCHAR with no options at all. The brief's flat claim — "DuckDB will happily read `007` as integer `7`" — is false for this version.

But:

```
I3: 30,000 numeric rows, then a single '007' on the last line
    → typeof(v) = BIGINT, 30001 rows
I3c: SELECT v FROM ... WHERE v IN (7,6)
    → 6, 7, 7          ← TWO rows now hold the value 7
```

**The `007` was silently converted to `7`.** The sniffer only inspects the first `sample_size` rows (default 20480). A leading-zero value beyond that window is never seen, the column types BIGINT, and the value is destroyed at scan time with no error.

Two mitigations, both verified:

```
A2: read_csv(..., all_varchar=true)   → VARCHAR ✅
K1: read_csv(..., sample_size=-1)     → VARCHAR ✅   (full-file sniff)
```

**Why this is the most dangerous finding in the set:** it is *position-dependent*. Every small test fixture passes. `scripts/test-parse.js` passes. A developer trying it by hand passes. The corruption only appears on real files past 20k rows — which is exactly the size range this migration exists to serve, and well within the current 50,000-row cap. **Landmine 6.1 stands, and `all_varchar=true` remains mandatory.**

The same window explains the sibling failure:

```
I1: 30,000 numeric rows then 'abc' → column types BIGINT
I1c: → Conversion Error on line 30002: Could not convert string "abc" to 'BIGINT'
     (ignore_errors=true does not rescue the row count either — I2 still reports 30001)
```

A late non-numeric value is a **hard scan-time error**, not a silent null. Loud, at least.

## 3. Row order — nondeterminism proven, mitigation verified

The strongest empirical result in this run. Same query, same data, three consecutive executions:

```
H: SELECT string_agg(k,'') FROM (SELECT k FROM (... 1,000,000 rows, 7 groups ...) GROUP BY k)
   run 1 → 6053412
   run 2 → 6015234
   run 3 → 6052134
```

**Group order varies between runs of an identical query on identical data.** Finding F2 is not theoretical, and the failure mode is confirmed as *intermittent* — a test suite would go red unpredictably, which is far worse to debug than a clean break.

Every piece of the proposed mitigation works:

| Experiment | Result |
|---|---|
| `G3` `GROUP BY k ORDER BY min(o)` via an alias | ✅ reproduces first-seen order |
| `G6` bare aggregate in `ORDER BY` | ✅ accepted |
| `G5` `ORDER BY n DESC, min(o) ASC` tiebreaker | ✅ stable |
| `G2` `QUALIFY row_number() OVER (PARTITION BY k ORDER BY ord) = 1` | ✅ correct first-wins survivor for `dedupe` |
| `I4` 400×400 join, `ORDER BY l.i, r.i LIMIT 50000` | ✅ 50,000 rows, no memory issue |

The `__ord` column strategy is sound and the join cap is safe.

## 5. What changes in the Phase 0 conclusions

**Unchanged.** F1 (sync vs async) — untouched by these results, still the blocking decision. F2 (row order) — now *proven*, not suspected. F4 (keep the formula front end) — reinforced: `1/0`→`inf`, `sqrt(-1)` throwing, RE2 rejecting backreferences and lookbehind, and no UTF-16 length are all confirmed hard walls. F5 (chart gaps) — not testable here; unchanged.

**Improved.** The float-summation hazard is refuted. `date_diff` already matches Tableau semantics. `UNION ALL BY NAME` already unifies to VARCHAR the way `appendTables` does. Quoted-empty, header trimming, and JSON key order all match. `sum(VARCHAR)` fails loudly rather than lying. Roughly a third of the Tier 1/2 mitigations get simpler.

**Worse.** Ragged-row handling has no faithful `read_csv` configuration. The whitespace class is split awkwardly between `trim` and RE2. And the `007` corruption is *position-dependent*, which makes it invisible to every small test.

**Revised Tier 1 (silent wrongness), after measurement:**

1. `007` beyond the sniffer's 20,480-row sample window → silently becomes `7` (A1 vs I3)
2. `SUM(INTEGER)` → `HUGEINT` → BigInt across the IPC boundary (D4)
3. `count()` over-counts `''` and whitespace-only cells (E8)
4. `max()` returns `NaN` when a column contains one (D6)
5. Ragged rows: the default read **drops the header and the short row** (B1)
6. `min`/`max` of a text column returns a string where the app returns `null`
7. Text `!=` against a NULL cell inverts a row's fate (F3)
8. `mode()` tie-break unspecified (G4)

Dropped from Tier 1: `sum` of a text column (now Tier 2 — binder error), and float summation drift (refuted).

## 6. Reproducing this

```bash
brew install duckdb   # 1.5.5
mkdir -p fx && cd fx
printf 'code\n007\n012\n'                > leadzero.csv
printf 'id\n12345678901234567890\n'      > bigint.csv
printf 'a,,c\n1,2,3\n'                   > emptyhdr.csv
printf 'a,a\n1,2\n'                      > duphdr.csv
printf 'a,b\n"",\n'                      > quotedempty.csv
printf 'a,b,c\n1,2\n3,4,5,6\n'           > ragged.csv
printf 'a,b\r1,2\r3,4\r'                 > lonecr.csv
printf 'a,b\n1,2\n\n3,4\n'               > blankline.csv
printf 'a,b\n"unclosed,2\n'              > unclosed.csv
printf '  a  ,b\n1,2\n'                  > padhdr.csv
printf 'a,b\nx"y"z,2\n'                  > midquote.csv
printf 'val\n$5\n$6\n'                   > currency.csv
printf 'a;b\n1;2\n'                      > semi.csv
printf '[{"a":1},{"b":2,"a":3}]'         > keyorder.json
python3 -c "open('latezero.csv','w').write('v\n' + '\n'.join(str(i) for i in range(30000)) + '\n007\n')"
```

Then run the statements from §4 with `duckdb -csv -c "<sql>"`. The order-determinism probe (H) must be run at least three times to observe the variation.
