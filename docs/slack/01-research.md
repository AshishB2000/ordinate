# BI Slack bots broadcast the asker's view

Every BI tool here that answers in a Slack or Teams channel runs the query under one identity, usually the linked asker's, and then posts the answer where every channel member can read it. None of the ten documents a check on whether the other members could see the same rows. Lightdash goes deepest, and it is one of only two tools here (with Metabase) whose Slack Q&A bot runs on the customer's own infrastructure, yet its default is weaker still: unless an admin turns on the **AI Agents OAuth requirement**, every Slack question runs with the permissions of whoever installed the Slack app, and its own open issue (12 November 2026) admits that "Lightdash cannot hide a Slack message from some channel members" ([Lightdash #32511](https://github.com/lightdash/lightdash/issues/32511)). The controls the market offers instead are coarse: private replies with a share button (Omni, Databricks Genie, and Hex for "Sensitive" connections), link-only replies whose link checks access again when opened (Lightdash, Hex), binding a channel to one curated agent or model (Lightdash, Databricks, ThoughtSpot), and pinning a thread to the person who started it (ThoughtSpot, Hex). Power BI sidesteps the problem by having no channel bot at all, since answers live in each person's own Microsoft 365 Copilot chat. On delivery, Lightdash and Metabase both have each customer create its own Slack app from a manifest and receive events through the HTTP Events API, which needs a public HTTPS endpoint; Lightdash also offers Socket Mode but still needs public image routes, and Metabase has no Socket Mode and no event deduplication. For Ordinate, whose row access rules and hidden columns are per user, the evidence supports a stricter default than any vendor ships: never post figures in externally shared channels, post them publicly only when every channel member is a linked user whose effective row rules and hidden columns on the touched datasets match the asker's, and otherwise post a short public acknowledgement while the full answer goes privately, with a link that re-runs under each viewer's own rules.

Throughout, **Vendor facts** are cited from docs, source code or issues, all read on 14 November 2026, and **Inference** marks my own reading rather than anything a vendor states.

## Lightdash maps the whole design space, including the unsolved half

Lightdash is the most useful reference for Ordinate because it is the only tool here whose Slack AI runs on customer infrastructure and also comes with a published manifest, readable source and a public issue tracker, and that tracker is where the shared-channel problem gets argued in the open. The Slack AI code sits in the enterprise directory (`packages/backend/src/ee/`), changes several times a week, and was read on `main` the same day as the docs, whose Mintlify pages carry no dates.

### One app, @mentions only, and threads mirrored read-only

**Vendor facts.** A person asks by @mentioning the single Lightdash app in a channel the bot has joined; the agent answers in a thread, every follow-up must @mention the app again, and a bare mention gets a fixed welcome that ignores the agent's description ([Lightdash: Set up agents in Slack](https://docs.lightdash.com/agents/set-up-slack-agents)). The one exception is the org's **multi-agent channel**, where a new top-level message needs no mention and is routed to the best-fit agent, though thread replies there still need one. Until 2 November 2026 the router answered every top-level message in that channel, and an opt-in "Only respond when mentioned" setting arrived only with [PR #31907](https://github.com/lightdash/lightdash/pull/31907), after [issue #30989](https://github.com/lightdash/lightdash/issues/30989). The source registers only `app_mention`, `message` and Block Kit action handlers (agent picker, channel linking, feedback, SQL approval, retry), so there is **no slash command and no App Home** ([ee SlackService.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/SlackService/SlackService.ts)). **DMs are not supported**: a Lightdash-authored issue says the bot "does not answer DMs" ([#31467](https://github.com/lightdash/lightdash/issues/31467)), and the self-hosted manifest subscribes only to `app_mention`, `link_shared` and `message.channels` ([Lightdash: Configure a Slack app](https://docs.lightdash.com/self-host/customize-deployment/configure-a-slack-app-for-lightdash)), although the docs never say so outright.

The agent reads only the text of the triggering message. With the admin's **AI Agents thread access consent** turned on, it also reads that thread, "including messages that didn't mention it", through `conversations.replies` capped at 100 messages, and it never sees attached images or files ([Lightdash: Slack integration](https://docs.lightdash.com/integrations/slack); [AiAgentService.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/AiAgentService/AiAgentService.ts)). Each Slack thread is stored as one Lightdash thread, keyed by channel ID and `thread_ts`. The web app shows that thread with the input disabled ("The thread was started in Slack") and without a Share button, and it cannot be deleted from the thread list because "that wouldn't remove the messages from Slack" ([Lightdash: Use AI agents](https://docs.lightdash.com/agents/use-ai-agents)). Admins see every conversation, from Slack or the web, under Threads ([Lightdash: Visibility](https://docs.lightdash.com/agents/visibility)), and Slack offers no model picker ([Lightdash: Set up agents](https://docs.lightdash.com/agents/set-up-agents)).

**Inference.** Slack is the only place a Slack-started conversation can be continued, which keeps each thread under one permission context at the cost of continuity. Because the multi-agent handler accepts only `channel_type === 'channel'`, a private channel set as the multi-agent channel probably still needs a mention; the docs do not confirm this.

### Installer identity is the default, and per-user OAuth is a toggle

**Vendor facts.** "By default, every AI agent conversation in Slack is attributed to the user who installed the Slack app (or created the agent)", and "every query runs with that user's permissions"; turning on the **AI Agents OAuth requirement** makes each Slack user authenticate so that queries respect "each user's own user attributes and permissions" ([Lightdash: Slack integration](https://docs.lightdash.com/integrations/slack)). **The docs disagree on who the default identity is**: the Data access page says "the attributes of the user who created the agent" ([Lightdash: Data access](https://docs.lightdash.com/agents/data-access)), while a code comment says Slack without the toggle "resolves the actor to the workspace installer, not the requester" ([AiAgentService.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/AiAgentService/AiAgentService.ts)).

The link itself is made with Sign in with Slack, through `passport-slack-oauth2` with the scopes `openid identity.basic`. It refuses to run without an existing Lightdash session, and it stores the Slack user ID and team ID as an OpenID identity on that Lightdash user, recording the Lightdash email rather than Slack's ([slackStrategy.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/controllers/authentication/strategies/slackStrategy.ts)). At question time the bot looks the sender up by Slack user ID, and the install never requests `users:read.email` ([slackSettings.ts](https://github.com/lightdash/lightdash/blob/main/packages/common/src/types/slackSettings.ts)). The code then handles three refusal cases ([AiAgentService.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/AiAgentService/AiAgentService.ts)). An unlinked sender gets an ephemeral "Connect your Slack account" button, and after the OAuth callback the original message is processed. A linked user who is not in the org gets an ephemeral "not a member" notice. A user who is denied the agent gets a refusal posted in the thread where everyone can read it, and that agent-access check runs only when the OAuth toggle is on. The beta, Enterprise-only agent permissions (behind the `agent-identity` flag) add "Who can use agents" groups covering Ask AI, Slack, MCP and the CLI. They check access live, so if someone loses access mid-answer the remaining messages are not posted, and Slack shows only the first line of a refusal ([Lightdash: Agent permissions](https://docs.lightdash.com/agents/agent-permissions)).

**Inference.** The link proves "this Slack account belongs to this signed-in Lightdash user" without trusting a Slack email, which suits a tool whose sign-in is the company IdP. The default is the problem: with the toggle off, anyone who can post in a mapped channel uses that agent with the installer's rights, and the installer is typically an admin. On 26 October 2026 Lightdash removed a hidden system-agent fallback because "anyone who could mention the bot could query data" ([PR #31596](https://github.com/lightdash/lightdash/pull/31596)), yet its default still carries the same kind of risk.

### Three stacked layers decide what a Slack question can reach

**Vendor facts.** Three layers stack ([Lightdash: Data access](https://docs.lightdash.com/agents/data-access)). **Agent tags** decide "which explores and fields the agent can see at all". **User attributes** (`sql_filter`, `required_attributes`, `any_attributes`) decide "which rows, columns and tables the asking user gets". **Raw SQL** is gated by the `manage:SqlRunner` permission, a per-thread SQL mode and the agent's data scope. Agent instructions "can't widen what it reaches". The model never connects to the warehouse either: Lightdash compiles and runs the query, using the asker's saved warehouse credentials where a project requires personal credentials (same page).

User attributes "do not apply" in SQL mode, and that is why Slack fails closed without OAuth: SQL mode, content editing, dbt writeback, repository discovery, dashboard previews and "pass user information" are all off under the shared identity ([Lightdash: Use AI agents](https://docs.lightdash.com/agents/use-ai-agents); [Lightdash: Content tools](https://docs.lightdash.com/agents/enable-content-tools); [AiAgentService.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/AiAgentService/AiAgentService.ts)). Warehouse query tags mark Slack runs with `agent_surface=slack_agent` ([Lightdash: Agent identity](https://docs.lightdash.com/agents/agent-identity)). Two weaker spots are documented. Metadata-only mode tells the model not to state figures, but "that is guidance to the model, not a check on its reply" ([Data access](https://docs.lightdash.com/agents/data-access); open [#31515](https://github.com/lightdash/lightdash/issues/31515)). Link unfurls always use the installer's credentials, so previews reflect "that user's data access — not the permissions of whoever shares the link" ([Lightdash: Slack integration](https://docs.lightdash.com/integrations/slack)).

**Inference.** The fail-closed list is the part most worth copying, because it gives an unverified chat identity less trust instead of quietly lending it the installer's rights. Unfurls are a second, quieter leak, and any Ordinate design must hold them to the same rules as answers.

### Answers post publicly, and Lightdash says it cannot hide them

**Vendor facts.** Answers post publicly in the channel thread; only the connect, link and refusal prompts are ephemeral, and the docs say nothing about members with different access, Slack Connect or ephemeral answers. Lightdash's open issue [#32511](https://github.com/lightdash/lightdash/issues/32511) (12 November 2026) states the gap plainly: with OAuth on, "the query runs as the asker, but the reply lands in a channel thread that everyone in the channel can read". The same issue concedes that **Links only** is org-wide, that "the agent still reads the rows and can describe them in its text reply", that link previews can still show chart data, and that the channel allowlist "controls where the bot answers, not who can read the answer". Its proposed fix is an ephemeral reply, a DM or a Lightdash link behind a short public acknowledgement, plus a per-agent Slack posture and a catalog-only mode. An earlier issue, [#31467](https://github.com/lightdash/lightdash/issues/31467), argued the other side: "Everyone in the channel sees every question, and that visibility is part of how they govern access." It proposed a "public channels only" toggle checked with `conversations.info` on every prompt, closed the same day, and no doc shows the toggle shipped.

What exists today is narrower. **Links only, no data in Slack** is org-wide, sends no chart images or CSVs, and uses a system prompt that forbids "numbers, totals, row counts, names, dates, rankings"; the in-repo guide says to "Pair with data access off on the agent for a strict guarantee" ([Slack integration](https://docs.lightdash.com/integrations/slack); [systemV2SlackLinksOnly.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/ai/prompts/systemV2SlackLinksOnly.ts); [AiAgentService/AGENTS.md](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/AiAgentService/AGENTS.md)). Turning off automatic channel linking makes the channel list a strict allowlist, the multi-agent channel can be restricted to chosen projects ([Set up agents in Slack](https://docs.lightdash.com/agents/set-up-slack-agents)), and the router "only chooses between agents the user can already access" ([Lightdash: AI Router](https://docs.lightdash.com/agents/enable-ai-router)). Even feedback is public, since an upvote posts "<@user> upvoted this answer" in the thread ([AiAgentService.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/AiAgentService/AiAgentService.ts)).

**Inference.** Lightdash controls who may ask, never who may read. With OAuth on, a privileged asker can broadcast rows that a channel neighbour's user attributes would hide; with OAuth off, everyone broadcasts the installer's view. Links-only is the only mode that keeps data out of Slack, and its guarantee about the text rests on a prompt unless data access is also off. Even the most mature self-hostable product calls asker-scoped delivery a known gap and has not shipped it.

### A channel, not a person, picks the agent

**Vendor facts.** A Lightdash org has one Slack app, so nobody @mentions a specific agent: "Lightdash routes your question to the most appropriate agent, and prompts you to choose if it's unclear" ([Slack integration](https://docs.lightdash.com/integrations/slack)). A regular channel is bound to exactly one agent through that agent's Integrations → Slack list, and binding a second agent fails with "This Slack channel is already assigned to another AI agent" ([Set up agents in Slack](https://docs.lightdash.com/agents/set-up-slack-agents)). The one org-level multi-agent channel offers every eligible agent through the **AI Router**, an LLM that compares each agent's description, instructions, data access and verified questions, plus optional per-project routing instructions. With one candidate the router picks that agent; with several it lets the model choose and falls back to an in-thread picker when confidence is low ([AI Router](https://docs.lightdash.com/agents/enable-ai-router); [AiAgentService/AGENTS.md](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/AiAgentService/AGENTS.md)). In an unbound channel, an asker who manages exactly one agent (holding `manage:AiAgent`) gets that agent linked and answered in the same turn, an asker who manages several gets a picker, and an asker who manages none gets an ephemeral message to contact an admin ([Set up agents in Slack](https://docs.lightdash.com/agents/set-up-slack-agents)). The web app's default agent has no Slack equivalent ([AI Router](https://docs.lightdash.com/agents/enable-ai-router)).

**Inference.** The channel is the routing key, and that maps directly onto Ordinate's per-team agents: binding a channel to a team's agent is the cheapest way to keep a channel on governed datasets. DMs would need a per-user default agent, which Lightdash never built.

### Answers arrive as text, then native tables and server-drawn PNGs

**Vendor facts.** By default the agent answers with a text summary, adding a native Slack `data_table` only "when it's requested or the rows help the answer". The code caps that table at 200 rows by 20 columns with an "omitted" note, and raw-SQL answers get a card that links to the results, "never an inline table" ([Slack integration](https://docs.lightdash.com/integrations/slack); [slackTableBlocks.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/ai/utils/slackTableBlocks.ts)). The model picks attachments by writing `<slack-table queryUuid="…"/>` and `<slack-chart versionUuid="…"/>` markers, which the server strips out ([AiAgentService/AGENTS.md](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/AiAgentService/AGENTS.md)). Charts are PNGs drawn on the server with ECharts on node-canvas at 800×600 and twice the pixel ratio, covering bar, horizontal bar, line, area, scatter, pie and funnel charts. A big number posts as text, custom chart types are drawn by the headless browser, and a feature flag swaps bar and line charts for Slack's native `data_visualization` block, at most two per message ([renderEcharts.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/ai/utils/renderEcharts.ts); [chartConfig/slack/AGENTS.md](https://github.com/lightdash/lightdash/blob/main/packages/common/src/ee/AiAgent/chartConfig/slack/AGENTS.md)). Lightdash itself warns that because Slack charts skip the web renderer, "a chart can be right in the app and wrong in Slack" (same). Images follow the text in a separate scheduler job that patches the message on retry ([SlackArtifactImageDelivery.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/AiAgentService/SlackArtifactImageDelivery.ts)).

Cards carry buttons such as **Explore in Lightdash**, **Open image**, **Open in SQL Runner**, **View dashboard**, or PR and Preview, and only turns that ran a query or built something get **Good**/**Bad** buttons and an **Open agent thread** link ([getSlackBlocks.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/ai/utils/getSlackBlocks.ts); [Slack integration](https://docs.lightdash.com/integrations/slack)). SQL approval works from Slack for a linked user who passes the server's SQL-approval check, and replies post under the agent's name through `chat:write.customize` ([AiAgentService.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/AiAgentService/AiAgentService.ts)). No "View SQL" button was found for answers from the semantic layer.

**Inference.** Drawing charts without a browser keeps Slack answers fast and needs no browser container, but it is a second chart implementation that can drift from the first. That is the same "two implementations must agree" problem Ordinate already polices with differential tests.

### Self-hosted events land on any pod and become Postgres jobs

**Vendor facts.** Lightdash Cloud uses a shared app installed with **Add to Slack** ([Slack integration](https://docs.lightdash.com/integrations/slack)), while a self-hosted deployment creates its own app from a manifest that points both events and interactivity at `https://<host>/slack/events` and leaves Socket Mode, token rotation and org-wide deploy off ([Configure a Slack app](https://docs.lightdash.com/self-host/customize-deployment/configure-a-slack-app-for-lightdash)). **Socket Mode** is available through `SLACK_APP_TOKEN` and `SLACK_SOCKET_MODE=true` for instances that "cannot expose" themselves to the internet, but "Socket Mode only covers events and interactions": Slack still downloads chart images from `SITE_URL` under `/api/v1/slack/`, so that path must stay reachable over public HTTPS (same page). In HTTP mode Bolt's `ExpressReceiver` is mounted on the main Express app; in Socket Mode a separate receiver runs and the OAuth redirect is wired by hand ([SlackClient.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/clients/Slack/SlackClient.ts)).

A mention can land on any API pod. That pod authenticates the sender, resolves the agent, silently drops a duplicate prompt with the same channel and timestamp, sets the "thinking" status and enqueues a `slackAiPrompt` scheduler job; chart images are a second job with claim and retry state and a 55-second abort ([AiAgentService.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/AiAgentService/AiAgentService.ts); [SlackArtifactImageDelivery.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/AiAgentService/SlackArtifactImageDelivery.ts)). With S3 storage the PNG is served from `/api/v1/slack/card-image/<id>`; without it the file is written to the pod's `/tmp` and delayed image delivery is skipped ([AiAgentService.ts](https://github.com/lightdash/lightdash/blob/main/packages/backend/src/ee/services/AiAgentService/AiAgentService.ts)). License keys, provider settings and the `agent-identity` flag must be set on every backend, scheduler and worker ([Lightdash: Self-hosted AI agents](https://docs.lightdash.com/self-host/enterprise-features/ai-agents); [Self-hosting Enterprise Edition](https://docs.lightdash.com/self-host/enterprise-features)).

**Inference.** The HTTP path suits stateless replicas because Postgres holds the installation, the prompt row and the queue, so any pod can take the POST and any worker can answer. Two weak points remain. The duplicate check reads first and inserts afterwards, so two near-simultaneous Slack retries could both insert unless a unique index exists, which I did not verify. And without S3, an image written to one pod's `/tmp` will 404 when Slack's fetch reaches another pod. Under Socket Mode every backend opens its own WebSocket, which runs into Slack's 10-connection limit, covered in the delivery section below.

### Setup needs an Enterprise license and a fixed 14-scope manifest

**Vendor facts.** The self-hosted manifest lists 14 bot scopes (`app_mentions:read`, `channels:join`, `channels:read`, `channels:history`, `chat:write`, `chat:write.customize`, `files:read`, `files:write`, `groups:read`, `groups:history`, `links:read`, `links:write`, `users:read`, `im:write`) with the instruction "Keep every bot scope in the manifest" ([Configure a Slack app](https://docs.lightdash.com/self-host/customize-deployment/configure-a-slack-app-for-lightdash)). The code's install request does not match it: it asks for `reactions:write`, which the manifest lacks, and does not ask for `channels:join` or `im:write` ([slackSettings.ts](https://github.com/lightdash/lightdash/blob/main/packages/common/src/types/slackSettings.ts)), and an open issue records that "Slack rejects the OAuth install when the app manifest does not include a requested bot scope" ([#31530](https://github.com/lightdash/lightdash/issues/31530)). The required env vars are `SLACK_CLIENT_ID`, `SLACK_CLIENT_SECRET`, `SLACK_SIGNING_SECRET` and `SLACK_STATE_SECRET` ([Lightdash: Environment variables](https://docs.lightdash.com/self-host/customize-deployment/environment-variables)).

**Slack AI is not in the open-source edition.** Agents carry Pro and Enterprise badges ([AI agents](https://docs.lightdash.com/agents); [Feature badges](https://docs.lightdash.com/support/feature-badges)), Cloud Pro starts "From $3000/ month" with "AI agents and MCP (usage-based)" ([Lightdash pricing](https://www.lightdash.com/pricing)), and self-hosting needs an Enterprise license key, `AI_COPILOT_ENABLED=true` and an LLM provider ([Self-hosted AI agents](https://docs.lightdash.com/self-host/enterprise-features/ai-agents)). Lightdash has **no Teams agent**; Teams appears only as a destination for scheduled agent charts ([Use AI agents](https://docs.lightdash.com/agents/use-ai-agents)).

## Nine other tools fall into three camps

The remaining nine tools sort into three groups. ThoughtSpot, Hex, Omni, Sigma, Metabase and Databricks Genie each ship their own chat bot that runs as the linked asker, and of these only Metabase's bot runs on customer infrastructure. Tableau (through Slackbot and MCP) and Looker (through Gemini Enterprise and its Conversational Analytics, or CA, API) have turned themselves into tool servers for someone else's assistant. Microsoft's Power BI has no channel bot at all. Only ThoughtSpot and Databricks ship a Q&A bot for Teams.

### ThoughtSpot treats a channel answer like a file shared there

**Vendor facts.** Spotter runs as an app inside Slack and Microsoft Teams and is "on by default for ThoughtSpot Cloud" ([ThoughtSpot blog](https://www.thoughtspot.com/blog/spotter-ai-analyst-in-slack-and-microsoft-teams); [Spotter in Slack 26.11](https://docs.thoughtspot.com/cloud/26.11.0.cl/spotter-app-for-slack)). In Slack a person DMs Spotter directly, or in a channel runs `/invite @Spotter` and tags it at the start of a question, or in a group DM tags it anywhere, where it reads earlier messages and on later tags "the messages since its last reply". A thread is one conversation and a new top-level message starts a new chat; answers "usually arrive in under a minute", users must "wait for one answer before you ask the next question", and four slash commands exist (`/spotter-help`, `/spotter-status`, `/spotter-show-models`, `/spotter-show-columns`) ([Spotter in Slack 26.11](https://docs.thoughtspot.com/cloud/26.11.0.cl/spotter-app-for-slack); [Spotter in Slack, latest](https://docs.thoughtspot.com/cloud/latest/spotter-slack)). In Teams the user asks in a 1:1 chat or tags `@Spotter` in a channel, with the text commands `help`, `status`, `show models`, `show columns` and `reset`; thread context "requires administrator permission", and group chats and private channels are **not supported** ([Spotter in Teams](https://docs.thoughtspot.com/cloud/latest/spotter-ms-teams); [ThoughtSpot blog](https://www.thoughtspot.com/blog/spotter-ai-analyst-in-slack-and-microsoft-teams)).

Each person links once, from **Profile → Connect to Slack** or **Connect to MS Teams**, and when an expired token makes Spotter stop answering, the fix is to "connect again from your profile" ([26.11](https://docs.thoughtspot.com/cloud/26.11.0.cl/spotter-app-for-slack)). Answers run "under the permissions of the person who asked", and "Row-level and column-level security rules apply exactly as they do in ThoughtSpot" ([latest](https://docs.thoughtspot.com/cloud/latest/spotter-slack)). On shared channels ThoughtSpot is blunt: everyone in a channel sees an answer, "the same as a file shared in the channel", and if someone else asks a follow-up in the asker's thread, Spotter tells them to start their own chat under their own permissions ([26.11](https://docs.thoughtspot.com/cloud/26.11.0.cl/spotter-app-for-slack)). Spotter picks the most relevant data model for each question, labels each answer "Answering using <model name>", asks when unsure, and lets anyone pin a model to a DM, channel or group DM; in Teams that choice "applies to everyone in the channel" ([26.11](https://docs.thoughtspot.com/cloud/26.11.0.cl/spotter-app-for-slack); [Teams](https://docs.thoughtspot.com/cloud/latest/spotter-ms-teams)). Text and tables appear inline, charts post as images "labeled with the question and the Model behind it", users can ask for a PDF or CSV, and Teams answers stream as they are written ([26.11](https://docs.thoughtspot.com/cloud/26.11.0.cl/spotter-app-for-slack); [blog](https://www.thoughtspot.com/blog/spotter-ai-analyst-in-slack-and-microsoft-teams); [Teams](https://docs.thoughtspot.com/cloud/latest/spotter-ms-teams)). Spotter needs a "ThoughtSpot-managed address", custom domains and the embedded UI are unsupported, and the docs leave the scope list to the Slack Marketplace listing ([latest](https://docs.thoughtspot.com/cloud/latest/spotter-slack)).

**Inference.** ThoughtSpot is the closest shipped analogue to Ordinate's feature, and two of its governance moves map directly onto Ordinate's agents: the thread stays with its first asker, and the model is pinned per channel and named in every answer. Beyond calling a channel post a share, though, it has nothing for mixed-access channels, and being Cloud-only and vendor-hosted, it never faces the self-hosted event problem.

### Hex pins each Slack thread to the person who started it

**Vendor facts.** People tag `@Hex` in a new message or thread, or DM the app, in public or private channels the bot has joined; a "..." reaction shows while it works and a checkmark when it is done, and in channels every follow-up needs a fresh mention ([Hex: Hex Agent in Slack](https://learn.hex.tech/docs/share-insights/hex-agent-in-slack)). Each answer is backed by a Hex **Thread** and links to it, and "only the Thread creator can ask follow up questions" (same). Users link one by one through Connected apps settings and need the Admin, Manager, Editor or Explorer role, with Threads turned on for Explorers. Permissions are "inherited from Threads", so the agent searches every connection "included for AI and that the user has access to", starting with the default connection (same).

The privacy control lives on the connection. Admins mark connections **Sensitive**, and some per-user OAuth connections are locked as Sensitive ([Hex: data connection access](https://learn.hex.tech/docs/api-integrations/hex-agent-data-connection-access), summary only). For those connections the admin chooses one of three Slack behaviours: **Reply privately**, which "posts a public reply with a link to Hex, and sends the full response as a private Slack message that only the requester can see" and lets the requester share it; **Reply with a link**, where "Anyone who opens the link must authenticate"; or **Do not use sensitive connections** ([Hex: Hex Agent in Slack](https://learn.hex.tech/docs/share-insights/hex-agent-in-slack)). The Threads link is "Shared with the workspace by default" in channels and private in DMs, and Hex advises private channels "when channel-wide visibility is a concern" and separate channels per data domain (same). Answers carry text, an explanation of the agent's work, charts and project links ([Hex blog, 29 Oct 2025](https://hex.tech/blog/introducing-agent-in-slack-and-mcp/)). Scopes are described only as "read and write access", the feature needs the Team plan or above and uses AI credits, and on Slack Enterprise Grid "Some functionality may not work as expected" ([Hex: Slack integration](https://learn.hex.tech/docs/api-integrations/slack)). There is no slash command, App Home, per-channel setting or Teams bot.

**Inference.** Hex's "Reply privately" is the clearest shipped version of a public acknowledgement plus a private answer, but it applies per connection rather than per row rule, so rows from a connection not marked Sensitive still post publicly. The docs don't say whether the private message is ephemeral or a DM, and that matters because ephemeral messages vanish on reload.

### Omni ships the strongest privacy switches of the SaaS tools

**Vendor facts.** Omni takes questions through DMs (which need the optional `im:history` scope, without which users fall back to `/omni ask`), channel @mentions, newly started group DMs, an App Home tab, and the slash commands `/omni ask`, `/omni model`, `/omni privacy`, `/omni disconnect` and `/omni help` ([Omni: Slack Agent](https://docs.omni.co/integrations/omni-slack-agent); [Omni blog, 22 Apr 2026](https://omni.co/blog/introducing-the-omni-slack-agent)). Threads are multiplayer: "Follow-up queries run against the permissions of the person asking", the first question sets the data model for the thread, and the agent "handles one request per thread at a time" ([Omni blog](https://omni.co/blog/introducing-the-omni-slack-agent)). Omni matches Slack users to Omni users by email through `users:read.email` but still requires a **Connect account** click, after which it picks up the original question unless that question came through `/omni ask` ([Omni docs](https://docs.omni.co/integrations/omni-slack-agent)). Access in Slack "mirrors their access in the Omni app", including "access grants, user attributes, and connection-level permissions", and Omni says it "will never use someone else's access" ([docs](https://docs.omni.co/integrations/omni-slack-agent); [blog](https://omni.co/blog/introducing-the-omni-slack-agent)).

By default, "If you ask a question in #revenue-review, the whole channel will see the answer" ([blog](https://omni.co/blog/introducing-the-omni-slack-agent)). The admin setting **Require private responses** makes every answer private with a **Share to channel** button; otherwise each user can toggle `/omni privacy`, and admins can lock that choice ([docs](https://docs.omni.co/integrations/omni-slack-agent)). Data scope comes from an admin default model, a per-user `/omni model` choice and the `ai_chat_topics` model parameter. Answers mix text with auto-linked dashboard names, Block Kit tables, image attachments when the file scopes are granted, an **Open in Omni** link and thumbs feedback with reason forms, and the agent can also create routines and skills and edit dashboards. The docs publish 15 required scopes and an optional set that includes `assistant:write` for "Future Omni functionality"; removing scopes needs a reinstall, and the admin's Disconnect deletes every user link and every scheduled Slack delivery (same). There is no Teams agent.

**Inference.** In Omni one thread can hold answers computed under different people's permissions, and a reader cannot tell which view a given answer reflects. "Never use someone else's access" describes how the query runs, not who reads the result; the privacy switch is what actually protects row rules, and it is off by default.

### Sigma's beta answers only linked users and says nothing about channels

**Vendor facts.** Sigma's Slack Q&A is a **private beta** that runs through the existing "Sigma Notifications" app (another page calls it "Sigma"), and Support or an account executive turns it on ([Sigma: Configure an agent for the Slack app](https://help.sigmacomputing.com/docs/configure-an-agent-for-the-slack-app); [Sigma: Manage Slack integration](https://help.sigmacomputing.com/docs/manage-slack-integration)). Every DM message gets a threaded reply, while in channels and threads the agent answers only direct mentions "by members who have connected their Sigma account" and stays silent otherwise. Linking is a **Connect Sigma** button that leads to an **Allow** page, and users need the Use Assistant permission. Answers use "the permissions associated with your Sigma account". An admin picks one agent for the whole org, either Sigma Assistant or a Snowflake Cortex or Databricks Genie agent, and the last two "must be available to all users"; a person narrows a question by pasting a link to a table, data model, semantic view or workbook. The agent posts each step as it works, offers **Show plan** listing "the queries it ran", and answers chart requests with an exported image plus a link to a newly created workbook (all from [Configure an agent](https://help.sigmacomputing.com/docs/configure-an-agent-for-the-slack-app)). The docs say nothing about mixed-access channels or Slack Connect. Sigma's launch blog says its Assistant in general "respects existing warehouse permissions, including row-level security and column masking" and promised Slack and Teams "coming soon" ([Sigma blog, 13 May 2026](https://www.sigmacomputing.com/blog/introducing-sigma-assistant), summary only), but for Teams only exports and notifications exist today ([Sigma: Manage Microsoft integration](https://help.sigmacomputing.com/docs/manage-microsoft-integration.md)).

**Inference.** The rule that a warehouse agent must be available to all users suggests the Slack path cannot pick an agent per user, and whether a Genie or Cortex agent then runs under the user's own warehouse identity is unknown.

### Metabase runs an open-source bot that posts every channel answer publicly

**Vendor facts.** Metabot in Slack shipped in Metabase 60 (April 2026), is "available on every Metabase plan", works self-hosted with your own AI provider, and lives in the open-source tree under `src/metabase/slackbot/` ([Metabot in Slack](https://www.metabase.com/docs/latest/ai/metabot-slack); [Metabase AI settings](https://www.metabase.com/docs/latest/ai/settings); [config.clj](https://github.com/metabase/metabase/blob/master/src/metabase/slackbot/config.clj)). A DM needs no mention, channels need an @mention, and the bot can sit in Slack's AI-app sidebar; its manifest subscribes to `app_mention`, `message.channels`, `message.im`, `assistant_thread_started` and other events, and defines no slash commands ([Metabot in Slack](https://www.metabase.com/docs/latest/ai/metabot-slack); [config.clj](https://github.com/metabase/metabase/blob/master/src/metabase/slackbot/config.clj)). The first message "kicks off an OAuth flow that connects the two accounts" through Metabase's own `/auth/login`, after which the bot looks up the Slack user ID in a link table with **no email matching**, and an unlinked asker in a channel gets an ephemeral connect prompt ([Metabot in Slack](https://www.metabase.com/docs/latest/ai/metabot-slack); [api.clj](https://github.com/metabase/metabase/blob/master/src/metabase/slackbot/api.clj)). Queries run as the linked user, and "Metabot in Slack doesn't read query results, regardless of the query-results setting", so the model never sees rows there ([Metabase AI settings](https://www.metabase.com/docs/latest/ai/settings)).

Channel answers are visible threaded replies. The docs only warn that "everyone in that channel can see the response", and the code has no ephemeral answers, no membership check and no handling for shared channels ([channel.clj](https://github.com/metabase/metabase/blob/master/src/metabase/slackbot/channel.clj); [events.clj](https://github.com/metabase/metabase/blob/master/src/metabase/slackbot/events.clj)). Metabot searches all content the asker can see, with no per-channel binding ([Metabot in Slack](https://www.metabase.com/docs/latest/ai/metabot-slack)). Replies stream through Slack's `startStream`/`appendStream`/`stopStream` calls, show tool progress as task updates, embed server-rendered PNG charts from a pool of 8 threads, end with Good/Bad feedback buttons, and are capped at 12,000 characters in channels ([streaming.clj](https://github.com/metabase/metabase/blob/master/src/metabase/slackbot/streaming.clj)). For setup, Metabase generates a manifest and the admin pastes a bot token, client ID, client secret and signing secret, with encryption at rest required ([Set up Slack](https://www.metabase.com/docs/latest/configuring-metabase/slack)). The manifest uses the Events API only (`socket_mode_enabled false`) at `<site-url>/api/metabot/slack/events` and requests 19 bot scopes, including `chat:write.public` and `channels:join` ([config.clj](https://github.com/metabase/metabase/blob/master/src/metabase/slackbot/config.clj)), which a self-hosted user's security team asked to make optional ([#75995](https://github.com/metabase/metabase/issues/75995)). The events handler acks and then hands the work to a thread pool inside the process, with **no `X-Slack-Retry-Num` handling and no event-ID deduplication** ([api.clj](https://github.com/metabase/metabase/blob/master/src/metabase/slackbot/api.clj)). There is no Teams bot.

**Inference.** Metabase is the cleanest example of keeping the model away from the figures in Slack, and the weakest on channel exposure and on running several instances. A slow ack could make Slack retry onto another instance and produce a duplicate answer, and a pod that dies mid-answer drops it; both risks come from reading the code, and no issue reports them.

### Databricks Genie lets channel owners pin an agent and admins force private answers

**Vendor facts.** Databricks hosts the Genie apps for Slack and Teams, relaying through its own infrastructure (`us-west-2` for Slack, East US 2 for Teams) that stores only the mapping to your workspace ([Genie app for Slack](https://docs.databricks.com/aws/en/genie-one/genie-slack); [Genie app in Teams](https://docs.databricks.com/aws/en/integrations/msft-teams)). In Slack a person uses the app's Chat tab in a DM or mentions `@Genie` in channels and newly started group DMs; in Teams they mention `@Databricks Genie` or DM it and type `newchat` to start over; and a channel owner runs `/databricks-genie config` in Slack or `config` in Teams (same pages). Each user clicks **Connect to Databricks** and signs in to a workspace, after which Genie answers "using the credentials of the Slack user who mentions @Genie", governed by Unity Catalog, on a SQL warehouse the user can access but cannot choose ([Slack](https://docs.databricks.com/aws/en/genie-one/genie-slack); [Teams](https://docs.databricks.com/aws/en/integrations/msft-teams)).

Databricks is the one vendor that documents both the leak and a control. "Responses are public by default", and everyone in the channel sees them, "including members who do not have access to the underlying data". A channel owner or user can make responses private (ephemeral), but "Visualizations don't appear in private messages", and private messages vanish on reload, device switch or app restart ([Slack](https://docs.databricks.com/aws/en/genie-one/genie-slack)). In Teams, visibility is set at workspace, channel and personal level with the higher level winning, and an admin toggle, **Allow public messages in collaboration platforms**, makes "all responses ... private to the user who asked" ([Teams](https://docs.databricks.com/aws/en/integrations/msft-teams)). Only the requester can answer tool-approval cards, and admins can allow Slack, Teams, both or neither, with changes taking up to an hour. A channel owner can pin one Genie Agent for the whole channel; without a pin the channel uses Genie One, a router that "might rewrite a question before it reaches a pinned agent" ([Slack](https://docs.databricks.com/aws/en/genie-one/genie-slack)). Answers carry text with sources and suggested follow-ups, visualizations "as an image", a **View conversation** button and thumbs feedback. The Teams app requests the Entra permissions `offline_access` and `User.Read` plus resource-specific consent (RSC) permissions such as `ChannelMember.Read.Group` and `ChannelMessage.Read.Group` ([Teams](https://docs.databricks.com/aws/en/integrations/msft-teams)).

**Inference.** Databricks shows what ephemeral answers really cost, since they lose charts and disappear, which is likely why public stays the default and the strict switch is left to an admin.

## Self-hosted delivery hinges on a 3-second ack and a 10-socket cap

### Slack platform facts that constrain a self-hosted bot

**Vendor facts.** Under the HTTP Events API, Slack sends one POST per event, expects a 2xx within three seconds, and retries up to three times (almost immediately, then after one minute, then after five), with `x-slack-retry-num` on each retry and `x-slack-no-retry: 1` available to stop further ones ([Slack Events API](https://docs.slack.dev/apis/events-api/)). Each event carries an `event_id` that is "globally unique across all workspaces", though the page does not tell apps to deduplicate on it. Delivery is capped at 30,000 events per workspace, per app, per hour, and subscriptions are temporarily switched off when more than 95% of deliveries fail within an hour for apps receiving 1,000 or more events an hour (same page). Requests are signed with HMAC-SHA256 over the timestamp and the raw body, and apps should reject timestamps more than five minutes off ([Verifying requests from Slack](https://docs.slack.dev/authentication/verifying-requests-from-slack)).

Under **Socket Mode**, an app may hold **at most 10 WebSocket connections**, and "each payload may be sent to any of the connections". It connects with an `xapp-` app-level token through `apps.connections.open`, must acknowledge every envelope by its ID, and must handle connection refreshes "once every few hours"; Socket Mode apps are not allowed in the public Slack Marketplace, and the page states no ack deadline ([Using Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode)).

On distribution, Slack's May 2025 terms call the Marketplace "the only appropriate channel for commercially distributing apps" and throttle unlisted, commercially distributed apps to 1 request a minute and 15 objects on `conversations.history` and `conversations.replies`, while "Internal customer-built applications are not impacted" ([Slack changelog, 29 May 2025](https://docs.slack.dev/changelog/2025/05/29/rate-limit-changes-for-non-marketplace-apps)). Every self-hosted product in this evidence has each customer create its own app, including Lightdash ([Configure a Slack app](https://docs.lightdash.com/self-host/customize-deployment/configure-a-slack-app-for-lightdash)), Metabase ([Set up Slack](https://www.metabase.com/docs/latest/configuring-metabase/slack)), Tableau Server ([Integrate Tableau Server with Slack](https://help.tableau.com/current/server/en-us/slack_admin.htm)) and Sentry ([Sentry docs PR #12235](https://github.com/getsentry/sentry-docs/pull/12235/files)).

Posting has its own constraints. `files.upload` was retired on 12 November 2025, so uploads now take two steps, `files.getUploadURLExternal` then `files.completeUploadExternal` ([files.upload](https://docs.slack.dev/reference/methods/files.upload/); [files.completeUploadExternal](https://docs.slack.dev/reference/methods/files.completeUploadExternal)). **Ephemeral messages are fragile**: "Ephemeral message delivery is not guaranteed", they "do not persist across reloads, desktop and mobile apps, or sessions", they appear in a thread "only if there is already an active thread", and they cannot be updated ([chat.postEphemeral](https://docs.slack.dev/reference/methods/chat.postEphemeral)). The `table` block holds up to 100 rows and 20 cells per row ([Table block](https://docs.slack.dev/reference/block-kit/blocks/table-block)), the newer `data_table` block holds up to 20 columns ([Data table block](https://docs.slack.dev/reference/block-kit/blocks/data-table-block/)), and a data visualization block shipped in June 2026 with no published limits ([Slack changelog, 16 Jun 2026](https://docs.slack.dev/changelog/2026/06/16/block-kit-data-visualization-block/)). The AI-app surface `assistant_view` is deprecated in February 2027 in favour of `agent_view`, a switch that "cannot be reversed" and that needs Marketplace review for distributed apps ([Slack changelog, 20 Aug 2026](https://docs.slack.dev/changelog/2026/08/20/agent-updates); [Migrating to Agent messaging](https://docs.slack.dev/ai/migrating-to-agent-messaging)), and posting is limited to about one message per second per channel ([Rate limits](https://docs.slack.dev/apis/web-api/rate-limits)).

The vendors sit at different points on this map. Lightdash uses HTTP by default with Socket Mode as an option, but still needs public image routes. Metabase uses HTTP only, with no dedupe. Google's Looker sample uses Socket Mode. Tableau Server never receives events at all, since it only pushes notifications out. Every SaaS vendor receives events on its own endpoint, and Databricks relays all Slack traffic through one region.

### What this implies for delivery in Ordinate (inference)

The per-customer app is the right model. Ordinate would ship a generated manifest with the instance URL filled in, the way Lightdash, Metabase and Tableau Server do, and the operator would create the app and paste its secrets. This is the only model with no vendor service in the data path, it keeps the app "internal customer-built" so it keeps full `conversations.*` rate limits, and it matches Ordinate's "no surprise network calls" rule.

The Events API should be the default, because it fits "any pod serves any request" directly. Any pod takes the POST, checks the signature against the raw body, records `event_id` in Postgres under a **unique constraint** (rather than Lightdash's read-then-insert), acks within three seconds and enqueues the work as a job, so that a Slack retry hits the constraint and is acked as a no-op. Socket Mode belongs as an option for firewalled installs, with an explicit cap of at most 10 pods opening sockets and the same dedupe table. Chart images should go up through the two-step file upload rather than being served from an instance URL. That removes Lightdash's leftover need for public image routes, so a Socket Mode install needs no inbound internet access at all, and it removes the pod-local image file that breaks behind a load balancer. Given the one-message-per-second-per-channel limit, the bot should post once at the end or use Slack's streaming calls rather than issue many message edits.

Scopes should be minimal. `chat:write.public`, `channels:join` and the `*:history` scopes should stay optional, as Omni makes them, because Metabase's #75995 shows security teams block exactly those. The notes give the minimal set for a mention-and-DM bot as `app_mentions:read`, `chat:write`, `im:history`, `im:read`, `im:write`, `users:read`, `channels:read`, `groups:read` and `files:write`, plus `assistant:write` for the AI surface, though they flag the purpose of each scope as unverified background knowledge rather than checked one by one against Slack's docs.

Ordinate's existing rules carry over unchanged. The bot token, signing secret and client secret belong in the secrets store with a canary test, every outbound Slack call goes through the SSRF guard, and no SQL text goes into Slack, which is simply another browser under the "no dataset origin reaches a browser" rule. There is also a chart-path choice to make: if Ordinate's charts render only in the browser, a Slack PNG needs a second, server-side renderer that carries Lightdash's admitted drift risk, and the alternative is Slack's native table and chart blocks fed with rows the server computed. Teams is a separate project, because the evidence covers only vendor-hosted Teams bots (ThoughtSpot, Databricks) that a Microsoft 365 admin installs and consents to, and says nothing about how a self-hosted product would register and receive Teams traffic.

## Shared channels need an audience check that no vendor ships

### Ten patterns, from broadcast to refusal

**Vendor facts.** Across the ten BI tools and the non-BI precedents in the evidence, ten patterns appear.

| Pattern | Documented by | Holds per-user row rules? | Main cost |
|---|---|---|---|
| Broadcast under the asker's rights ("sharing a file") | ThoughtSpot, Metabase, Lightdash with OAuth; the default for Omni, Hex and Databricks | No; the asker hands their view to the whole channel | None, which is why it is the default |
| Shared service identity | Lightdash default, Copilot Studio author auth, Looker API user, Tableau MCP PAT | No; every asker gets one account's rows | Silent privilege escalation |
| Private reply plus a share button | Omni, Databricks, Hex (Sensitive connections), Glean | Yes, until shared | Ephemeral replies vanish; Databricks loses charts |
| Public acknowledgement, full answer private | Hex "Reply privately"; proposed in Lightdash #32511 | Yes | The channel loses the shared context |
| Link only, access checked again on open | Lightdash links-only, Hex "Reply with a link", Tableau Pulse details pane, Looker unfurls | Yes, if the text carries no figures | An extra click; Lightdash enforces it with a prompt |
| Gate on what every member can access | Glean Public Mode, M365 Copilot group chats, Tableau's snapshot rule | Partly; checks sources, not rows | Over-restricts; costs a check per member |
| Pin a thread to its first asker | ThoughtSpot, Hex | Prevents mixed views inside a thread | Others must start again elsewhere |
| Bind a channel to a curated agent | Lightdash, Databricks, ThoughtSpot | Only if the channel's members match the agent's audience | Membership changes over time |
| Refuse when external members are present | Glean; Slack's own guidance | Yes, for outsiders | Blocks use in Slack Connect channels |
| Compute under every member's rules | Nobody | Roughly | Answers a different question from the one asked |

Three precedents from outside BI fill in the picture. Glean answers privately by default with "only data the user is authorized to access", and its admin-enabled Public Mode posts to the thread but draws only on "broadly shared content" ([Glean: Manage permissions and security](https://docs.glean.com/administration/platform/embedded-integrations/slackbot/admin-guide/manage-permissions-security); [Glean: Understand Public Mode](https://docs.glean.com/user-guide/embedded-integrations/slack/understand-public-mode)); a community thread shows the cost, since Public Mode hides SharePoint content that channel members could in fact open ([Glean community](https://community.glean.com/discussion/918/make-slack-option-c-follows-with-sharepoint-permissions-at-document-folder-level)). Microsoft Copilot in Teams group chats, when an answer used sources not every member can access, gives the asker a preview "visible only to them" to approve or reject ([Copilot in Teams chats](https://support.microsoft.com/en-us/office/copilot-in-teams-chats-2c613de4-cd26-4ae3-9e4b-6905d745d991)). GitHub for Slack suppresses previews of private repositories unless the person who shared the link has connected an account and agreed to show them ([GitHub docs: Use GitHub in Slack](https://docs.github.com/en/integrations/how-tos/slack/use-github-in-slack)). Slack itself tells apps to "default to exposing less information in shared channels", says an app "must ask for confirmation" before sharing sensitive internal data with an external partner, and notes that slash commands work only for users of the installing workspace ([Slack Connect for apps](https://docs.slack.dev/apis/slack-connect/)). Channel type is readable, because `conversations.info` exposes `is_ext_shared`, `is_org_shared` and `is_private`, and an external user shows up through `team_id` and `is_stranger` (same page; [users.info](https://docs.slack.dev/reference/methods/users.info)).

### What the patterns imply for a self-hosted Ordinate (inference)

Ordinate can check the audience precisely where vendors cannot. Its engine computes every figure and every reader takes the row lock, so at answer time the server knows exactly which datasets an answer read and which row rules and hidden columns shaped it for the asker. No vendor's Slack layer uses that much, and it makes the right test cheap to state: **equal policies, not an intersection of rows**. For each dataset the answer touched, the server compares the asker's effective row rules and hidden columns with each channel member's. If every member's lock is identical, every member would compute the same figures, so posting publicly discloses nothing new. If any member fails, because of a different lock, an unlinked account, no access to the agent or project, or membership of another Slack org, the answer is not safe to broadcast. Datasets with no row rules and no hidden columns pass at once, so in most channels most answers cost one access check per member. Intersecting the rows themselves would answer a different question from the one asked, would need every member linked, and is documented by no vendor.

That check supports a layered default stricter than any vendor's. First, there is no shared-identity mode at all, since Lightdash's installer default and the system-agent fallback it removed show where that leads. Second, linking is required, through Sign in with Slack from a live Ordinate session, keyed on team (or enterprise) ID plus user ID and never on email, which is the Lightdash and Metabase model; an unlinked asker gets an ephemeral connect prompt, and the original question resumes after linking. Third, each channel is bound to one team agent by someone who manages that agent, DMs use the user's default agent, and an unbound channel gets instructions instead of an answer. Fourth, no figures go into channels where `is_ext_shared` is true, and guests (`is_restricted`) are an explicit admin decision. Fifth, the audience check runs after the engine runs and before posting: if it passes, the answer goes publicly into the thread; if it fails, a fixed-template public acknowledgement with no model text and no figures goes to the channel, while the full answer goes by DM rather than as an ephemeral message (Databricks shows ephemerals lose charts and vanish), together with an **Open in Ordinate** link that re-runs under each viewer's own rules. Sixth, a Share to channel button re-runs the check, and if it still fails, an admin policy decides whether the asker may override it, off by default so that no asker can declassify data quietly. Seventh, a thread keeps its first asker's permissions as in ThoughtSpot and Hex, so another member's mention starts their own thread or DM, where Omni instead lets one thread mix views computed under different people's rules. Eighth, link unfurls follow the same rule as answers and never use installer credentials.

Whenever no figures should reach Slack, whether under a link-only posture or after a failed check, the rule should be enforced in structure rather than in a prompt. The model gets no rows, as in Metabase's Slack path, instead of Lightdash's prompt that forbids numbers, and that also keeps Ordinate's rule that a model only narrates figures an engine computed.

The check has real costs. It lists channel members on every answer (`conversations.members`, plus `users.info` for `team_id` and `is_stranger`, whose scopes and rate tiers the notes did not re-verify). Large channels need a cap above which the check simply fails, for which Microsoft's 60-participant cutoff on link previews is a precedent. The check also holds only at the moment of posting: Slack shows channel history to people who join later, so a public answer stays visible to future members whose rules differ, and for datasets with row rules the fully safe home is a private channel whose membership mirrors the team, an operator practice that no vendor documents as a feature. Finally, like every guard in Ordinate, the check needs a negative-control test proving that a mixed-access channel fails it.

## Where the sources conflict or run thin

On Lightdash, the docs name both "the user who installed the Slack app" and "the user who created the agent" as the default identity while the code says installer ([Slack integration](https://docs.lightdash.com/integrations/slack); [Data access](https://docs.lightdash.com/agents/data-access)); the published manifest and the code's scope request disagree ([#31530](https://github.com/lightdash/lightdash/issues/31530)); the "public channels only" toggle from #31467 may never have shipped; and no dated launch post for Slack agents was found. Among the other vendors, Tableau's Slackbot plus Tableau Cloud MCP status conflicts between the help page and the July 2026 release page, and since that page returned 403 the claim rests on a search summary. Metabase's Slack setup page lists "Metabot is set up on your Cloud instance" as a prerequisite, against "every Metabase plan" elsewhere ([Set up Slack](https://www.metabase.com/docs/latest/configuring-metabase/slack)). Databricks's GCP Slack page lists "no chart visualization" as a preview limit while the AWS page shows chart images ([GCP](https://docs.databricks.com/gcp/en/genie-one/genie-slack); [AWS](https://docs.databricks.com/aws/en/genie-one/genie-slack)). ThoughtSpot's Teams docs moved from early access to on-by-default over successive releases.

Some evidence is simply thin. Scope lists are unpublished for Hex, Sigma and ThoughtSpot, Hex and Omni never say whether a "private" answer is ephemeral or a DM, and Sigma's claim about row-level security comes from a general blog summary rather than its Slack doc. The duplicate-answer and lost-reply risks named for Metabase and Lightdash come from reading their code, not from incident reports. No independent user reviews or complaints turned up for any of these Slack agents, which is a gap in the evidence rather than proof that users are happy. The `data_table` cell-character cap is 20,000 in Slack's reference and 10,000 in a third-party write-up ([Classmethod](https://dev.classmethod.jp/en/articles/slack-block-kit-new-data-display-blocks/)), and Slack states no ack deadline for Socket Mode.

## Conclusion

The market's quiet consensus is that answering in a channel means sharing the asker's view, and no vendor treats that as a defect. Lightdash comes closest: its own tracker names the gap, and its earlier issue argues that channel visibility is itself how some teams govern access. The shared-channel problem is therefore less a missing feature than a missing input, because vendors' Slack layers never see the exact row policy behind each figure, while Ordinate's engine does, and that makes a precise policy-equality audience check possible without the approximations Glean and Microsoft accept.

On infrastructure, the self-hosted design is a solved problem, even though both reference implementations still leave gaps: Lightdash's public image routes and pod-local files, and Metabase's missing dedupe and retry handling. The open choices are about posture rather than plumbing: whether a failed audience check falls back to a DM or to a link, whether an asker may ever override it, and whether figures from row-ruled datasets should go anywhere but a private channel that mirrors the team.
